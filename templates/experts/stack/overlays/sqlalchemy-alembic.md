# SQLAlchemy + Alembic

Detection found `sqlalchemy` in the project's Python dependencies, with the evidence line
saying whether `alembic` is there beside it. The mapped models are the source of truth for
the schema, a generated revision is a draft until someone reads it, a session has a lifetime,
and a lazy relationship is a query waiting to fire once per row. The repo's own conventions
win over everything below — a Default applies only where the repo is silent, and a Check's
accepted answer is the project's existing pattern when it has one.

## Defaults (when the repo is silent)

- Treat the mapped models as the source of truth for the schema and change the database by
  changing them. — overridden by: a schema owner or migration tool the repo declares elsewhere
- Generate a revision from the models and then READ it before committing: autogenerate sees a
  drop and a create where you meant a rename, and it does not catch every constraint, server
  default or type change. — overridden by: the migration workflow the repo documents
- Keep one head: merge or rebase a revision that branched rather than leaving two tips for the
  next deploy to choose between.
  — overridden by: a branching scheme the repo documents for its revisions
- Scope a session to one unit of work — a request, a task, a test — and close it there; never
  create one at import time or share one across concurrent work.
  — overridden by: the session factory or dependency the repo already exports
- Use the asynchronous session only with an asynchronous driver, and keep off the async path
  the lazy loads that would block it.
  — overridden by: the engine and driver the project already configures
- Write queries in the style the surrounding modules already use rather than mixing both query
  styles inside one module. — overridden by: the prevailing style in the module you are editing
- State how a relationship loads at the query that needs it, instead of letting a lazy load
  fire once per row. — overridden by: the loading strategy already configured on the relationship
- Let the migration environment read the same configuration the application reads, so a
  migration cannot run against a different database than the app.
  — overridden by: the configuration the repo's migration environment already loads

## Checks (always asked in review)

- Does the diff change a model without adding the revision for it? verify: check whether the
  model change and a new revision file are both in this commit
- Was an autogenerated revision committed unreviewed — a drop and a create where a rename was
  meant? verify: read the new revision's upgrade and downgrade against the model diff
- Is there more than one head? verify: ask the migration tool for its heads and read what it
  prints; two tips mean the next deploy chooses arbitrarily
- Is a session created at import time, held across requests, or shared between concurrent
  tasks? verify: read the top-level statements and the session's lifetime in the modules the
  diff touches
- Is a relationship touched inside a loop, turning one query into one per row? verify: read
  each loop over query results added in the diff against the loading option on the query
- Does a new revision go without a downgrade, or with one that does not undo its upgrade?
  verify: read the new revision file end to end
- Does the migration environment read a different database location than the application?
  verify: open the migration environment file and the application's settings and compare where
  each one reads its connection details
